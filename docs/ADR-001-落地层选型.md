# ADR-001：改名落地层的选型

**状态**: 已定案
**日期**: 2026-08-19
**决策者**: 项目总指挥（经用户授权"按你的来"）

## 背景

需要把网盘里杂乱命名的媒体文件整理成飞牛/Emby 可刮削的规范结构。
落地动作（建目录 + 改名 + 移动）有三条可能路径：

| 方案 | 做法 | 预期优势 |
|---|---|---|
| A1 | 调各网盘 API 的 rename/move，在网盘内部整理 | 零流量；但三家 API 各写一套 |
| A2 | 在 CloudDrive2 的 fuse 挂载点 `/vol2/1000/CloudDrive/影视` 直接 `os.Rename` | 一套代码通吃三家 |
| A3 | 调 CloudDrive2 自身 API（:19798） | 一套代码，且不依赖 fuse 语义 |

上一轮我**推荐 A2**，理由是 `mount` 显示该挂载为 `rw`。

## 实测结论：A2 与 A3 均不可行

### A2 被证伪（三重验证）

1. **宿主机普通用户**：`mkdir` → `Permission denied`
2. **宿主机 root**（`sudo`）：`create file` / `rename` / `mkdir 中文目录` 全部 FAIL
3. **CloudDrive2 容器内部**（该挂载的拥有者进程，`/CloudNAS` 标记 `rw=true`）：
   ```
   mkdir: can't create directory '/CloudNAS/影视/.fnos-selftest/': Not supported
   ```

关键点：错误是 **`Not supported`（能力缺失）而非 `Permission denied`（权限不足）**。
且 `config.toml` 中该挂载 `read_only = false`，排除"CD2 只读开关"这一解释。

结论：**CloudFS 对该挂载类型不支持目录创建**，A2 从根本上不可行。

### A3 不可行

`:19798` 返回 HTTP 200，但 `/api`、`/v1`、`/swagger/index.html` 均 404，
首页特征表明是 **gRPC-web（protobuf）**，无公开 REST 契约。
逆向 protobuf 的成本高于直接实现 A1，且升级易碎。

## 决策

**采用 A1：网盘侧 API rename/move。**

- 各网盘（夸克 / 百度 / 光鸭）各实现 `Mkdir` / `Rename` / `Move`
- CloudDrive2 挂载退化为**只读投影**，供飞牛扫描刮削
- 改名器输出的是**云端目标路径**，落地器把它翻译成各网盘 API 调用

## 后果

- 成本上升：三套云端文件操作实现（原以为一套即可）
- 收益不变：零流量、无本地磁盘占用
- 附加约束：**落地前必须批量规划**（先算全量路径 → 消歧 → 碰撞检测 → 再动手），
  因为云端 API 的移动/改名不可批量回滚，出错代价远高于本地文件系统

## 教训

> "挂载显示 rw" ≠ "可写"。fuse 挂载的能力必须**实测**，
> 且要在**真正的执行主体**（拥有该挂载的容器内）测，而非仅在宿主机测。
> 本次若跳过验证直接按 A2 写代码，三套落地逻辑会全部报废。

## 修订（2026-08-20）：光鸭结论推翻 — A3 Alist API

### 原结论错在哪

本文档原先判定「光鸭无法落地」，依据是 CloudDrive2 的 CloudFS 挂载只读：
mkdir / rename / write 全部失败。该测试本身没错，**错在把「一种访问方式
不可写」当成了「这个网盘不可写」**。

我只测了 NAS 上的 CloudFS 挂载，没去查用户早已在跑的另一条链路。用户提示
「光鸭可以考虑 alist 跟 rclone 实现」后翻旧配置才发现，
`/vol2/apps/media-hub/data/alist/data.db` 里躺着一个 **GuangYaPan 驱动**，
`mount_path=/光鸭`、`status=work`、未禁用 —— 早就配好了。

教训：**判定某能力"不存在"之前，必须先清点现有基础设施**。用户环境里已经
跑通的东西，比我从零试出来的结论更可信。

### A3 实测结果

复制一份 Alist 数据库（原库不动）起独立容器验证：

| 能力 | 结果 | 验证方式 |
|------|------|---------|
| 列目录 | ✅ | `/光鸭` 返回 6 个子目录 |
| mkdir | ✅ | code=200 |
| rename | ✅ | **刷新列目录确认云端真落实**，非仅 200 |
| move | ✅ | 目标目录内确认到被移入项 |

真实规划（fnosctl land --alist，dry-run）：

    /光鸭/影视/电影    → 计划 16 | 失败 0 | 跳过 0，TMDB 全中
    /光鸭/影视/电视剧  → 计划 33 | 失败 0 | 跳过 0

### 为什么这不等于回到旧的重型架构

用户对 Alist 的顾虑是「太绕、占电脑资源」。旧 MediaHub 重在
**rclone FUSE + 50G VFS 缓存 + Emby 转码**，不在 Alist 本身。

落地只需改名，**不需要读文件内容**，所以：

| | 旧 MediaHub | A3 落地用法 |
|---|---|---|
| FUSE 挂载 | 要（含 50G 缓存） | **不要** |
| 常驻 | 7×24 | 整理时跑几分钟 |
| 宿主 | Windows/WSL | **NAS** |
| 用途 | 播放串流 | 只调 `/api/fs/rename` |

### 实现要点

Alist **没有「改名+移动」的单一接口**，跨目录落地必须两步。选择
「先在源目录内改成规范名，再 move」而非反序：move 时若目标目录残留同名
旧文件（上一轮中断留下的），Alist 行为不确定、可能覆盖；先改成规范名
（批内唯一性已由碰撞检测保证）再移动更安全。

对应实现：`internal/lander/alist.go`，接口抽象见 `backend.go`。
`MountBackend`（夸克/百度，os.Rename）与 `AlistBackend`（光鸭，HTTP API）
并列，由 `--alist` 选择。
