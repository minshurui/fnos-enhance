# ADR-001：改名落地层的选型

**状态**: 已定案
**日期**: 2026-08-19
**决策者**: 项目总指挥（经用户授权"按你的来"）

## 背景

需要把网盘里杂乱命名的媒体文件整理成飞牛/Emby 可刮削的规范结构。
落地动作（建目录 + 改名 + 移动）有三条可能路径：

| 方案 | 做法 | 预期优势 |
|---|---|---|
| A1 | 调各网盘 API 的 rename/move，在网盘内部整理 | 零流量；但三家 API 各写一套 |
| A2 | 在 CloudDrive2 的 fuse 挂载点 `/vol2/1000/CloudDrive/影视` 直接 `os.Rename` | 一套代码通吃三家 |
| A3 | 调 CloudDrive2 自身 API（:19798） | 一套代码，且不依赖 fuse 语义 |

上一轮我**推荐 A2**，理由是 `mount` 显示该挂载为 `rw`。

## 实测结论：A2 与 A3 均不可行

### A2 被证伪（三重验证）

1. **宿主机普通用户**：`mkdir` → `Permission denied`
2. **宿主机 root**（`sudo`）：`create file` / `rename` / `mkdir 中文目录` 全部 FAIL
3. **CloudDrive2 容器内部**（该挂载的拥有者进程，`/CloudNAS` 标记 `rw=true`）：
   ```
   mkdir: can't create directory '/CloudNAS/影视/.fnos-selftest/': Not supported
   ```

关键点：错误是 **`Not supported`（能力缺失）而非 `Permission denied`（权限不足）**。
且 `config.toml` 中该挂载 `read_only = false`，排除"CD2 只读开关"这一解释。

结论：**CloudFS 对该挂载类型不支持目录创建**，A2 从根本上不可行。

### A3 不可行

`:19798` 返回 HTTP 200，但 `/api`、`/v1`、`/swagger/index.html` 均 404，
首页特征表明是 **gRPC-web（protobuf）**，无公开 REST 契约。
逆向 protobuf 的成本高于直接实现 A1，且升级易碎。

## 决策

**采用 A1：网盘侧 API rename/move。**

- 各网盘（夸克 / 百度 / 光鸭）各实现 `Mkdir` / `Rename` / `Move`
- CloudDrive2 挂载退化为**只读投影**，供飞牛扫描刮削
- 改名器输出的是**云端目标路径**，落地器把它翻译成各网盘 API 调用

## 后果

- 成本上升：三套云端文件操作实现（原以为一套即可）
- 收益不变：零流量、无本地磁盘占用
- 附加约束：**落地前必须批量规划**（先算全量路径 → 消歧 → 碰撞检测 → 再动手），
  因为云端 API 的移动/改名不可批量回滚，出错代价远高于本地文件系统

## 教训

> "挂载显示 rw" ≠ "可写"。fuse 挂载的能力必须**实测**，
> 且要在**真正的执行主体**（拥有该挂载的容器内）测，而非仅在宿主机测。
> 本次若跳过验证直接按 A2 写代码，三套落地逻辑会全部报废。
